# Build and run an integrator

Use integrator tools to import Excel, CSV, or SQL source data. Confirm the connected customer first. Configuration/Admin access and the matching `ri:integrators.read`, `.write`, and `.run` scopes are required. An existing connection may need new consent for these scopes.

1. Call `search_integrators` to find reusable definitions. Read the selected definition with `get_integrator`; preserve its unchanged settings and latest conflict token. Use `get_integrator_folders` when placement matters.
2. Resolve the exact target feature with `search_features`. Use `get_fields` for writable field schema codes, types, references, and allowed value codes. Call `get_integrator_match_schema` for the required master/parent/target levels. Suggested identity fields are hints, not a declaration of uniqueness.
3. For files, obtain approval to stage the source. Call `stage_integrator_source_file` with a local `file_path`, or with `file_name` and then upload multipart field `file` to the returned signed URL outside model context. Sources accept CSV/XLSX/XLSM up to 25 MiB and expire after three days. Use the resulting `staged_file_id` for inspection and runs.
4. Call `inspect_integrator_source` to inspect sheets, headers, sample rows, distinct `value_columns`, and composite `key_columns`. Columns use Excel letters. For a headerless source use `header_row=0`, `first_data_row=1`, and set the integrator FirstDataRow to 1. CSV converts to worksheet `Source`, preserving text and leading-zero ids. Supply a delimiter when needed. Use `sheet_name`, `header_row`, and `first_data_row` for the real layout. Key checks cover at most 5000 rows; inspect the full source separately before claiming uniqueness. Workbook previews use cached formula values and raw stored date/numeric values.
5. For SQL, call `get_integrator_connections` and choose a configured connection/listener. Ask the administrator to configure missing credentials or install a listener through the existing setup workflow. Save a source draft, then queue an approved `test_connection`, `scan_headers`, or `query`. Write provider-appropriate SQL with an explicit exploration limit. Query mode suppresses Realinsight posting, but SQL can still change its source database. The existing source runner reports zero-row execution results as an error; use a header scan to inspect an empty result schema.
6. Build the full `definition` using its typed schema. Its configuration properties retain PascalCase names. Choose `ProcessType=DICTIONARY`, the discovered `ProcessTypeCode`, `DataSourceType=EXCEL` or `SQL`, and the matching source settings. Existing custom integrators use their custom dataset id and built-in extractor rules.
7. Define ordered `MatchLevels` from master through target. Each level needs an explicit `NewEntityAction`: `MATCH` updates existing matches only, `INSERT` matches or creates, and `INSERTONLY` inserts. Use source-backed composite keys unique within each parent. For entity references, set `ReferenceKeySchemaCode` to a field on the referenced feature. COA references use `ChartName` or `ChartId` and match existing charts. Periodic levels support `CURRENT`, `EARLIEST`, and `ALL`; `ALL` can target multiple periods. Verify representative target matches with entity query and record tools.
8. Set `Map` entries for fields on the target feature. Configure `ValueXref` with exact allowed target value codes, `IgnoreValues`, reference `MATCH`/`ADD` behavior, and COA account/value mappings where needed. Use chart-of-accounts tools to inspect real chart/account identities. Ancestor match levels do not receive ordinary data-map updates.
9. Call `set_integrator` with `dry_run=true`. Resolve `errors` before saving and `run_errors` before applying. `can_save` allows an incomplete mapping draft; `can_run` requires posting settings. Pass discovered `source_columns` to check source-column names. Validation does not simulate posting or guarantee key uniqueness.
10. Show the proposed source, key choices, match/insert behavior, mapped fields, value/reference/COA options, and warnings. After exact approval, save with `dry_run=false`, `approved=true`, and the latest `expected_conflict_token` for updates. The whole definition replaces existing configuration. Omitted `ParentFolderId` uses the integrator root; use a discovered folder id for requested placement. Optional `active` changes activation; omission preserves it.
11. Read the saved definition/token and queue approved `scan_headers` or `scan_values`. Poll `get_integrator_run` with both returned handle fields. Read `headers` or select a `scan_column` from `scan_columns` and page `values`. Value scans operate on mapped value-list fields. Correct mappings/translations and validate again.
12. Obtain separate approval of the exact apply operation. Call `run_integrator` with `mode=apply`, `approved=true`, the latest conflict token, and the file handle or declared SQL variable overrides. Keep the definition stable until execution finishes. Queue calls are non-idempotent: never automatically retry after a timeout or uncertain response.
13. Poll `get_integrator_run` until `is_complete`, then inspect `completion_code`, errors, and paged logs. SQL extraction finishing alone does not finish posting. Read-only sections include `status`, `logs`, `headers`, `values`, and SQL `rows`. Result paging does not limit source SQL work. Report truncation and preview limits.
14. Verify representative records through entity/record tools after apply. A saved definition, passed scan, completed extraction, and successful posting are separate evidence. Summarize the applied import and warnings for the user.

Local CLI equivalents use `ri-agent integrators search|get|folders|match-schema|connections|set|stage-source|inspect-source|run|status`. Complex requests accept `--request-file ./request.json`; scalar options use kebab-case. `--dry-run false` performs a save only with approval. A typical polling command is `ri-agent integrators status RUN_ID --run-kind sql --section logs --limit 50`.
